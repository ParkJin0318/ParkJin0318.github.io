요즘은 “한 번 만들어 놓고 끝”인 자동화보다, **매일 굴리는 개인용 에이전트**가 더 가치가 큰 것 같습니다.

다만 에이전트는 데모까지는 빨리 되는데, 실제로 쓰기 시작하면 아래에서 꼭 한 번씩 미끄러집니다.

- 어디까지 자동화했는지 기억이 안 남
- 툴/노드 연결이 불안정해서 자주 끊김
- 로그가 여기저기 흩어져서 장애 원인 파악이 늦음
- 결국 “귀찮아서 안 씀” 상태로 회귀

이 글은 제가 OpenClaw를 **개발자 개인용 운영 도구**로 세팅하고 굴리는 방식(설치 → 기본 설정 → 툴/노드 붙이기 → 운영 루틴)을 정리한 글입니다.

> 주의: OpenClaw는 버전/환경에 따라 명령어나 설정 파일이 조금씩 다를 수 있습니다.
> 아래 내용은 “제가 운영하는 구조/원칙” 중심이고, **정확한 커맨드는 `openclaw help` 출력**을 기준으로 맞춰주세요.


## 왜 OpenClaw인가 (문제의식)

제가 원한 건 대체로 이런 형태였습니다.

- 텔레그램 같은 채널에서 “할 일”을 던지면, 에이전트가 알아서 작업을 진행
- 필요하면 서브에이전트를 여러 개 띄워서 병렬로 조사/작성/수정
- PC/모바일 같은 실제 디바이스(노드)도 붙여서 카메라/화면/브라우저 같은 현실 자원을 사용
- **작업 기록이 파일로 남아서** 다음날 다시 이어가기 쉬움

OpenClaw는 이걸 “운영 가능”한 형태로 묶어주는 쪽에 강점이 있습니다.
특히 툴/노드/서브에이전트 분리가 깔끔해서, 확장하다가도 구조가 쉽게 망가지지 않더라고요.


## 전체 아키텍처 (제가 이해한 OpenClaw)

[다이어그램: OpenClaw 구성요소(메인 에이전트 / 서브에이전트 / 노드 / 툴 / 워크스페이스 파일)]

제가 쓰는 관점에서 핵심은 5가지입니다.

### 1) 메인 에이전트(Main agent)

- 사용자가 대화 채널(예: 텔레그램)로 요청을 넣는 창구
- 작업을 쪼개고(계획), 실행을 위임하고(서브에이전트), 결과를 합칩니다.

### 2) 서브에이전트(Subagent)

- “조사만”, “초안 작성만”, “코드 수정만” 같이 **역할을 좁혀서** 일시키는 실행 유닛
- 메인 에이전트가 `sessions_spawn` 같은 방식으로 생성하고, 결과는 자동으로 메인에게 돌아옵니다.

### 3) 노드(Node)

- PC/모바일 등 실제 디바이스를 붙이는 개념
- 제가 주로 쓰는 건:
  - 화면 캡처/녹화(재현, 문서화)
  - 카메라 스냅(현장 기록)
  - 원격 명령 실행(간단한 진단)

### 4) 툴(Tools)

- 에이전트가 실제로 할 수 있는 “손”
- 예: 파일 읽기/쓰기, 셸 실행, 브라우저 자동화, 웹 검색, 메시지 전송 등

### 5) 워크스페이스 파일(= 파일 기반 메모리)

저는 “대화는 휘발되고, 파일만 남는다” 쪽에 베팅합니다.

- `shared/MEMORY.md`: 장기 기억(중요한 의사결정, 팀 규칙)
- `memory/YYYY-MM-DD.md`: 일일 작업 로그
- `TOOLS.md`, `AGENTS.md`: 운영 규칙(툴 사용법, 안전장치, 위임 규칙)

이 구조를 잡아두면, 에이전트가 틀린 결정을 했을 때도 **다음 번에 같은 실수를 줄이는 장치**가 됩니다.


## 제가 제일 중요하게 둔 것: 멀티 에이전트 + Notion 태스크 관리

결론부터 말하면, “에이전트 똑똑함”보다 **운영 루프**가 훨씬 중요했습니다.

제가 쓰는 운영 루프는 이렇습니다.

1) 해야 할 일을 Notion에 쌓아둔다
2) 메인 에이전트는 Notion에서 “다음 할 일”을 집어온다
3) 작업을 잘게 쪼개서 역할별 서브에이전트에게 위임한다
4) 결과를 검증하고, Notion 상태를 업데이트한다

여기서 핵심은 두 가지입니다.

- **태스크의 단일 출처(SSOT)**: 할 일을 여러 곳(메모/슬랙/카톡/머릿속)에 두면 100% 누수납니다.
- **상태 전이 규칙**: Backlog → Active → Done(또는 Waiting). 이 규칙이 있어야 “매일 굴러갑니다.”

> 이 글에서는 API 토큰/DB 스키마 같은 세부 구현은 일부러 생략했습니다.
> (공개 글에서 민감정보/운영 디테일이 새는 걸 피하기 위해서입니다.)

[이미지: Notion 태스크 DB 예시(Backlog/Active/Done)]


## 제가 쓰는 운영 루틴 (아침 1분 + heartbeat)

운영은 “한 번 설치”보다 “매일 굴리기”가 더 중요해서, 루틴을 2겹으로 깔아두는 편입니다.

### 1) 아침: 상태 체크(1분)

- 게이트웨이가 살아있는지
- 메시지 채널 연결이 정상인지
- 어제 작업 로그가 남았는지

OpenClaw CLI에서 게이트웨이는 보통 이렇게 확인합니다.

```bash
openclaw gateway status
```

필요하면 재시작:

```bash
openclaw gateway restart
```

### 2) heartbeat: “죽었을 때 알아차리기”

자동화는 “잘 도는 날”보다 “죽은 날”이 문제입니다.
그래서 저는 최소한 아래 중 하나는 반드시 둡니다.

- (A) 주기적으로 상태 점검 → 비정상이면 알림
- (B) 일정 주기로 재시작(과격하지만 효과적)

[이미지: 알림 채널(텔레그램)로 ‘Gateway down → restart’ 메시지 오는 예시]

> 참고: 저는 개인적으로 주기적인 체크에 더 비중을 둡니다.
> “자동 재시작”은 최후의 안전장치 느낌으로요.


## 세팅 단계 (설치 → 기본 설정 → 스킬/노드 붙이기 → 운영)

### 0) 전제: 워크스페이스부터 잡기

워크스페이스에 아래 파일들은 꼭 둡니다.

- `TOOLS.md`: 사용할 수 있는 도구/스킬, 경로, 금지 패턴
- `AGENTS.md`: 에이전트가 지켜야 할 운영 규칙(예: 거짓 보고 금지, 위험 명령 확인)
- `shared/MEMORY.md`: 장기 기억
- `memory/YYYY-MM-DD.md`: 일일 작업 로그

이게 없으면 에이전트가 똑똑해도, 운영이 누수로 새기 시작합니다.


### 1) 설치/검증

환경마다 설치 방식이 다를 수 있어서, 저는 **설치 커맨드보다 검증 커맨드**를 먼저 적어둡니다.

```bash
openclaw gateway status
openclaw help
openclaw gateway --help
```


### 2) 기본 설정(채널/권한/작업 디렉토리)

제가 중요하게 보는 기본값은 다음입니다.

- **작업 디렉토리 고정**: 파일을 어디에 쓰는지 항상 예측 가능해야 합니다.
- **권한 최소화**: 처음부터 모든 걸 자동 승인하지 않고, 위험한 작업은 단계적으로 열어줍니다.
- **로그 경로 고정**: 장애가 나면 “어디서 봐야 하는지”가 제일 중요합니다.


### 3) 스킬/툴 붙이기 (웹/브라우저/셸/파일)

제가 자주 쓰는 조합은 아래입니다.

- 웹 검색/웹 페이지 가져오기: 조사/리서치
- 브라우저 자동화: 제품/어드민/대시보드 클릭 작업
- 셸 실행: 리포 클론, 빌드, 테스트, 포맷
- 파일 읽기/쓰기: 초안/리포트/로그 남기기

운영 팁은 한 가지입니다.

- “툴이 할 수 있는 일”을 늘리는 것보다,
- **툴이 실패했을 때 어떻게 복구할지**(재시도/타임아웃/폴백)를 먼저 적어두는 게 효율이 좋습니다.


### 4) 노드 붙이기 (모바일/서브 머신)

노드를 붙이면 “현실 자원”을 쓸 수 있어서 자동화 범위가 확 넓어집니다.

- 모바일 화면 캡처로 버그 재현 기록
- 현장 사진 찍어서 문서에 붙이기
- 특정 PC에서만 가능한 내부망 작업 위임

다만 노드가 붙는 순간부터 보안/프라이버시 고려가 필수입니다.

- 개인 화면(연락처/메신저/사진)이 노출될 수 있음
- 화면 녹화 권한이 필요한 경우가 있음

[이미지: 노드 페어링 화면 / 권한 허용 안내]


## 실전 팁

### 1) 실패 방지: 작업을 더 작게 쪼개기

에이전트에게 “한 번에 크게” 시키면, 성공해도 검증이 어렵고 실패하면 원인도 흐립니다.

- 조사 → 정리 → 실행 → 검증 → 기록

이 5단계로 쪼개서 서브에이전트에 분배하는 게 체감상 가장 안정적이었습니다.


### 2) 보안: 토큰/시크릿은 절대 글에 남기지 않기

제가 지키는 원칙:

- `.env`, `credentials` 같은 파일은 커밋 금지
- 스크린샷에도 토큰이 찍힐 수 있으니 모자이크/마스킹
- 에이전트 프롬프트에 토큰을 그대로 넣지 않기(가능하면 “파일 참조”)


### 3) 브라우저 Relay: “사람이 로그인한 브라우저”를 붙이는 방식

브라우저 자동화가 실전에 들어가면 결국 “로그인/2FA”에서 막히는 경우가 많습니다.

이럴 때 저는 **브라우저 Relay(확장 프로그램)로 기존 브라우저 탭을 붙이는 방식**을 선호합니다.

- 자동화 브라우저(격리된 세션)보다, 내가 이미 로그인해둔 Chrome 탭을 붙이는 게 운영이 쉽습니다.
- 다만 탭 연결(attach)이 되어 있어야 하고, 연결이 끊기면 다시 붙여야 합니다.

[이미지: Chrome 확장 프로그램에서 Relay 뱃지 ON 상태]


### 4) 자동화의 확장: (예) 투자/리서치

OpenClaw의 좋은 점은 “업무 자동화”에만 머물지 않고, 루틴성 작업을 넓게 담을 수 있다는 점입니다.

저는 개인적으로 특정 루틴을 붙여서 쓰고 있는데, 이 부분은 성격상 **여기서는 ‘가능하다’ 정도로만** 언급하겠습니다.
(대신 중요한 건: 자동 실행 범위를 좁히고, 로그/알림/검증을 필수로 두는 것입니다.)


## 한계/주의사항

- 자동화가 늘수록 “디버깅/관찰”의 중요도가 같이 올라갑니다.
- 노드/브라우저 자동화는 환경 의존성이 큽니다(권한, 화면 상태, 네트워크).
- 에이전트는 종종 확신 있게 틀릴 수 있습니다. 그래서 **검증 단계(테스트/체크리스트)**가 꼭 필요합니다.


## 다음 글(계획)

이 글은 세팅/운영 개요 수준이고, 다음은 분리해서 더 자세히 정리하려고 합니다.

- (1) Notion 태스크를 에이전트 루틴에 붙이는 방법(스키마/우선순위/재시도)
- (2) 서브에이전트 운영 패턴(역할 분리, 병렬화, 결과 합치기)
- (3) 장애 대응 플레이북(로그 수집, 재시작, 알림)
- (4) 브라우저 자동화 실전 패턴(로그인, 2FA, 안정적인 selector 전략)
